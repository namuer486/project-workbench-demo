# 研究资料进入项目拆解

IPD 报告不是独立的数据看板。报告里的六维评价、体验案例、结论和建议，与开发过程的问题记录一起进入项目拆解，形成项目级问题和通用经验。平台负责展示与追溯，GPT + Skill 负责有依据的结构化和提炼。

```text
IPD 研究报告 + 开发问题清单（仍在现有表格或公司知识库维护）
    ↓ GPT + ipd-report-json Skill
输入层：六维评价 / 研究案例 / 开发明细 / 原文依据
    ↓ 通过 ID 关联
项目级问题：目标 → KSF → 解决方案 → 复盘
    ↓ 有依据的归纳
通用性提炼：共性机制、经验与待验证假设
    ↓ report.json（schemaVersion 2.0）
平台导入预览 → 人工核对 → 提交仓库 → 构建内部静态工作台
```

## 页面与数据对应

| 页面内容 | JSON 字段 | 交互 |
|---|---|---|
| IPD 阶段与当前重点 | ipd | 当前阶段、关注重点和下一轮验证输入 |
| 六维体验拆解 | dimensions、cases | 原始指标与正负面案例；按维度筛选提炼 |
| 通用性提炼 | insights | 查看相关项目问题、开发明细、研究案例 |
| 项目问题时间轴 | projectProblems | 展开目标、KSF、方案和复盘；日期缺失独立显示 |
| 问题明细、每周总览 | issues | 保留源表编号、状态和已明确的方案 |
| 研究输入、原文依据 | study、sources、evidence | 报告作为支撑信息，核对结论出处 |

数量、未闭环数和明细负责人由平台按关联 ID 计算。项目级状态不拿开发明细的状态代填。满意率、原始分、加权分分别保留；缺失不填零，不同量表不直接比较。

## 给 GPT 的调用示例

> 用 $ipd-report-json，把这份 IPD 研究报告和开发问题清单拆解为项目工作台数据，项目 ID 用 my-project。报告信息进入六维评价、案例、项目级问题和通用性提炼，不单做报告可视化。项目问题按目标、KSF、方案、复盘展开，每条提炼关联具体案例和开发明细，保留原文依据。未知事实留空，推断和建议标 AI。输出 v2 report.json，运行校验后交付。

在普通 GPT 对话中，可一起提供 `skills/ipd-report-json/SKILL.md`、`references/contract.md`、`references/project.schema.json` 以及原始资料。参考 `example-project.json` 的格式，不把演示数据带入真实项目。

目前使用的是合成示例：撤离时机不清楚、危险位置难以共享，分别形成项目级问题，再提出“关键决策信息需要在行动前可见、可共享”的待验证假设。报告与问题表出现相同现象只表示交叉印证，不等于重复故障次数。

## 校验与保存

```powershell
python skills/ipd-report-json/scripts/validate.py path/to/report.json
```

校验结构、六维、数值范围、ID 唯一性、关联完整性、日期和依据；不证明原文摘录准确，也不证明 AI 提炼正确。默认 draft，人工核对后才能标 reviewed。

静态版网页点击「导入项目 JSON」仅本地预览，刷新后退出。本机服务版会先上传到服务器校验预览，点击「保存并生成项目」后持久保存；见[本机部署](本机部署.md)。静态仓库模式正式共享时提交到 `projects/my-project/report.json`，目录名与 `project.id` 一致。同项目不能同时放旧的 `project.json`。开发表仍是业务维护入口，生成 JSON 时将最新明细同步进 issues，再重新核对提炼关系。

v1 JSON 继续支持，首页会显示缺少项目级提炼，平台不自行编造。可将旧 JSON 和新资料一同交给 Skill 升级；复用稳定 ID。

静态网页不调用模型，不需要模型密钥，也没有新增问题提交入口。尚未接入公司知识库，也未用真实项目报告验收提取完整性。公开部署默认关闭；公司内部访问控制需覆盖网页和所有静态 JSON。
