# 仓库驱动的静态项目工作台

本方案不依赖 WorkBuddy。表格放在 Git 仓库中，构建任务读取表格并校验，生成 HTML、CSS、JavaScript 和 JSON，部署到静态托管服务。用户打开网站查看；策划继续维护原表，不新增问题录入系统。

当前要求是仅公司内部访问。工作流默认只构建，不开启 Pages 部署。实际部署时必须由托管平台或反向代理保护整个站点，包括 `data/*.json`。在网页里增加一个密码框不能保护已经公开的 JSON 文件。

## 数据更新流程

```text
维护 Excel 或在线表格
       ↓ 保存 / 导出
替换 GitHub 仓库里的问题表并提交
       ↓ 自动触发 GitHub Actions
校验字段、编号、状态、日期和标签
       ↓ 校验通过
生成静态看板与项目 JSON
       ↓ 发布到带公司访问控制的托管服务
团队访问固定地址查看最新结果
```

更新失败时构建终止，不会部署半成品，线上仍是上一次成功部署的数据。此流程不是浏览器实时读取私有 GitHub 仓库：读取仓库的是构建任务，浏览器读取的是已发布的站点数据。网站不携带 GitHub 访问令牌。

## 添加项目

每个项目一个目录：

```text
projects/
  demo/
    project.json
    issues.csv
  your-project/
    project.json
    issues.xlsx
```

可在静态网站左侧点击「生成项目配置」，填写项目名、起始日期、标签、版本和源表文件名，下载 `project.json`。把该文件和源表放入新的 `projects/项目代号/` 目录并提交即可，无需修改网页代码或单独部署。目录名使用小写英文、数字、下划线、短横线，最多 64 字符。

`projects/demo` 是明确标注的合成演示数据，上线真实项目时可以删除演示目录。

默认识别常见中文字段名：问题编号、问题内容、负责人、完成状态、提出日期、解决方案、优先级、功能分类、衡量标签、版本、解决日期。编号和问题内容必填。Excel 第一行是表头，第一张表默认作为数据表；需要指定时增加 `sheet` 配置。含公式的表请先粘贴为值。

如原有列名不同，可在 `project.json` 设置映射：

```json
{
  "name": "项目 A",
  "startDate": "2026-09-01",
  "stage": "核心玩法验证",
  "tags": ["目标感", "乐趣性"],
  "versions": [{"name": "v1.0", "startDate": "2026-09-01"}],
  "file": "issues.xlsx",
  "sheet": "问题台账",
  "mapping": {
    "id": "任务编号",
    "title": "描述",
    "owner": "责任人",
    "status": "处理状态",
    "date": "登记日期"
  }
}
```

可映射字段还有 `solution/priority/category/tags/version/resolvedAt`。省略 `mapping` 时自动识别；显式提供 `mapping` 时仅使用其中列出的字段。

静态模式每次以仓库的完整表格重新构建，删行意味着从下一次看板中移除；历史通过 Git 保留。要继续展示已关闭问题，请在表里标记已解决而不删行。这个行为与可选服务器模式的「缺失保留」不同。

## 本地查看

Windows 安装 Python 3.11 或更新版本后，可以双击仓库根目录的 `预览静态工作台.cmd`。首次启动自动建立环境并安装依赖，随后构建演示数据并打开本机页面。更改表格后再次运行即可生成新的预览。该入口不向互联网发布。

```powershell
python -m pip install -r platform/requirements.txt
python platform/build_static.py --output _site
python -m http.server 8766 --bind 127.0.0.1 --directory _site
```

打开 `http://127.0.0.1:8766`。输出目录需为空，避免误覆盖；再次构建可选择新的输出目录。页面使用相对资源路径，兼容 `https://主机/仓库名/` 这种项目路径。由于使用 fetch 加载 JSON，请通过 HTTP 预览，不要双击 HTML。

## GitHub Actions 和 Pages

工作流位于 `.github/workflows/workbench-pages.yml`：更新 `main` 的项目数据或平台代码会触发测试和构建，PR 也运行校验。只上传 `_site` 产物，不上传整个仓库。构建不需要长期存储的个人 GitHub Token。

在确认合适的访问控制之前，不启用公开发布。普通私有仓库不等于私有 Pages 网站。GitHub Enterprise Cloud 组织符合条件的私有或内部项目仓库可提供私有 Pages，访问者需有仓库读取权限。

如果确定使用已受保护的 Pages：

1. 在仓库 Settings → Pages 中选择 GitHub Actions，并按组织能力设置私有可见性。
2. 配置 `github-pages` 环境，仅允许 `main` 部署。
3. 在仓库 Actions variables 设置 `WORKBENCH_PAGES_ENABLED=true`。
4. 运行工作流或提交一次变更。

默认变量未设置，所以不会执行部署。没有 Enterprise 私有 Pages 时，将同一份 `_site` 产物部署到公司已有认证网关后的静态站点即可；具体适配待公司托管和身份系统明确后完成。本项目没有用静态分享链接代替身份认证。

整个静态站点的项目清单和 JSON 对所有获准访问站点的人可读。如果不同项目的访问成员不同，需要分别部署站点或由网关对各项目数据路径做授权；不能仅靠前端项目切换实现权限隔离。

## 后续知识库集成

每个项目输出 `data/<项目代号>.json`，保留稳定的问题 ID 和结构化字段。公司 AI 知识库后续可以在通过同一访问控制后拉取数据，或由构建任务主动推送到公司接口。当前没有连接公司服务，也没有把模型密钥放进网页。
